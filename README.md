# 问题一 · 钢包吊运与共轨行车调度

解压后进入 ladle 目录，使用 Python 3.10+。所有命令从该目录执行。


## 接口与口径

单位由调用方统一。示例一拍为一分钟，每车每拍移动一格。车辆编号从 0 开始。每个任务给定固定取放点与允许车号，可用不同边集限定车辆作业区。不同工位可以共享沿轨坐标，使用不同的资源名区分。窗前占位、固定工艺处理和连铸换中包均可作为 Problem.bookings 输入。处理位与接收位应分别命名，cast_bookings 的返回值须合入 bookings。固定 LF/RH 路线由调用方按工艺顺序拆段。渡车编号及对应坐标由场景给定。示例未读取生产表。

任务就绪为 upstream + alpha，最迟落包为 downstream − beta。source 从 upstream 占用到实际起吊加 release_lag；receiver 从落包占用到 downstream。若下一包已有到位安排，使用同一资源名或已有预约。单独使用 latest_pick 时须预先扣除释放滞后。接收位内可等待时长为最迟落包减实际落包。P95 使用最近秩定义。轨迹包括空车、静止车及避让移动，各拍内匀速，检查所有同步折点即可覆盖拍内的最小间距。

完整模型用时空弧和“任务–车–起吊拍”二元变量建立整数线性约束，以 SciPy/HiGHS 两次求解。先最小化所有任务总待吊，再固定已证最优待吊并最小化移动。若第一阶段限时，只以其待吊为上界，最终保留字典序较好的可行解。局部 DP 在相同拍、位置、任务及起落记录下，仅保留移动较少的状态。比较口径为相同输入、初位、预约和每次 10 秒预算。

optimal 表示该搜索范围内两个目标都已证最优，feasible 表示有完整可行解，infeasible 表示该离散模型已证无解，unknown 表示限时未判定。greedy_blocked 表示基线既有承诺阻止继续插单。异常输入给出 ValueError。部分插单的任务表仅用于定位失败，没有完整轨迹时不计算收益。

## 合成验收

五台行车中前两台执行三项任务，后三台驻车。基线总待吊 6、空驶 3；联合解总待吊 2、空驶 1。局部 DP 固定原方案出窗位置，得到总待吊 2、空驶 3。三者带包均为 5，最小间距均为 2。联合解落包后等待从 8 升至 12，不能据此推断总生产周期缩短。运行入口可看到每项起落点时刻、释放时刻、接收位预约和全部车位轨迹。

此版本面向小窗口与算法核验。轨道为一维有向单位格，重包走直达路径，车辆速度一致。连续时间、车辆异速、大规模生产时窗的性能和实际收益尚未验证。

# 问题二 · 工序波动下的钢包派车与提前待命

本项目按《问题二钢包派车与提前待命》第 1–6 节实现。输入是固定工艺路线、计划工时、历史工时块、工位与共轨行车参数。输出包括每段的开工、可吊、车辆到位、起吊、落包与开浇时刻，以及三组配对实验的指标。全部内部时间使用秒，位置使用米。文档两张手算表沿用分钟。

## 运行

解压后进入 `ladle_q2/`。Python 3.10 及以上可直接运行自带样本和测试，均只使用标准库。三个入口都从项目根目录通过模块方式启动。

```bash
python -m unittest discover -s tests -v
python -m runner.experiment_1_timing
python -m runner.experiment_2_scope
python -m runner.experiment_3_motion
```

默认窗口含 5 炉、12 段重包吊运、5 台共轨行车。三组实验使用相同的工时种子 27。控制台列出任务数、平均和 P95 待吊、连铸备包迟到率与修复次数。下列命令可保存逐单结果，查看首步选择和完整运动轨迹。

```bash
python -m runner.experiment_2_scope --case five-heats --samples 2 --draws 4 --traces --output results/my_scope.json
python -m runner.experiment_1_timing --case validation --world measured --q 0.50
python -m runner.experiment_3_motion --case holdout --world measured --output results/my_motion.json
```

| 参数 | 用法 |
|---|---|
| `--case` | `five-heats` 为指定的 12 段验收样本。另可选 `validation`、`holdout` 或 2026-10-05 至 2026-10-11 的单日窗口。 |
| `--world` | `sampled` 取联合抽样工时，`measured` 取入选炉实际处理工时，`both` 使用窗口内可用的两类输入。 |
| `--samples` / `--draws` | 前者为外层测试场景数，后者为实验二每次决策用于比较候选的独立预测场景数。增加后者会增加决策耗时。 |
| `--advance` / `--q` | 统一提前秒数，默认 120；条件分位数默认 0.25。设包等车、车等包成本分别为 3 和 1 时，成本公式给出 0.25。 |
| `--risk` | 实验二可设可接受的备包迟到率。超阈值时优先减小超出量。默认同时报告等待与风险，以总待吊、再以移动时长排序。 |
| `--rail` / `--dataset` | 替换轨道配置或抽取后的整炉样本文件。修改运动参数后，同一命令即可重新回放。 |

## 模型口径

1. **工时及信息边界。** 每项可吊时刻等于实际开工加处理工时与必要准备。首段按计划释放，后段由上一段真实模拟落包触发。工时样本优先匹配整条路线和设备，匹配不足 5 炉时合并为覆盖该工序组合的样本。整炉一次抽样，保留该炉各段关联。已完工时间用于匹配近邻供体，未完工样本按“工时大于已运行时长”筛选；超出经验上界时按低样本尾部规则外推。样本抽取和选择策略使用独立接口，调度器只能读取已发生事件。
2. **提前待命。** 离散分位数按累计概率首次达到阈值计算。统一提前量与分位数均可调。已派指令保持承诺，选择原地暂缓的单台车会在新事件到达时重评，其他车仍可派出。邻位待命后仍有最后一段空驶。目标包与其他包争车时，首步回放追踪整个窗口直至终段交接。
3. **共轨与容量。** 区段速度取负载档速、区段档位上限和物理限速的较小值。停车、换向及取放点速度为零，普通区段边界保持速度连续。每次提交运动前，对左右邻车的所有相位边界及区间内相对速度为零处做连续检查；其余时段按原地静止处理。额外保留已派车取放区间，工位从起吊时预留至下一次起吊或开浇。共享精炼位还要给同一连铸机早序炉保留入口。上述预留偏保守，可能舍弃可行的紧凑解。
4. **连铸和窗外任务。** 同机按开浇计划顺序接续，交接晚于期限记为备包迟到；只有同浇次且炉序相邻的交接参与模拟缺包计数。实绩断浇原因无法从所用记录独立确认，输出为 `null`。五炉局部窗口从首炉开工预热，取第二炉释放至第五炉释放为观察区间，保留窗首在制任务及各车位置、速度，并追完五炉。输出单列第五炉第一段的交付及参考期限；现场存在硬承诺时可通过 `Job.commitment` 输入，审计发现超限即标记失败。
5. **目标和指标。** 总待吊等于各包“起吊减可吊”的总和。报告按任务最近秩计算 P95。车等包累计取包点到达早于就绪的时间，落包后等待累计到实际下工序开工。移动和空驶以车秒计，行车占用从派出到落包统计。`repair_count` 是单段估时短于物理可执行时间而需顺延的指令数，`repair_seconds` 是这些指令的顺延秒数之和；决策计算耗时另计。按已实现可吊时刻，即使立即起吊仍赶不上期限的包，列入 `conditional_unavoidable_jobs`。
6. **策略比较。** 每对使用相同窗口、各炉外生工时与初始车位。实验二只提交首步，预测中的其余动作用同一非预知规则续派；新观测到来再选择。输出 `decisions` 可逐项核对候选排序。全批范围覆盖前后续、同车及邻车任务。指定风险阈值时，两组均核验全批连铸备包风险。
7. **区间。** `differences` 给出“本策略减第一种策略”的配对差值；同一日期先对场景取平均，再对日期整块有放回抽样 1,000 次。单窗口无跨日期区间，字段为 `null`。报告保留失败场景并返回非零退出码。只有两侧都完成的配对计入差值，`blocks` 与 `pairs` 给出实际样本量。

## 数据与适用范围

- `five_heats.json` 来自《炼钢吊运任务表.xlsx》和出钢计划。包含 26CD4985、26AD6492、26BD6185、26AD6493、26CD4986 五炉从转炉至连铸的 12 段重包运输。它位于数据期初，用预设的 0.8、1.0、1.0、1.2 倍工时做功能验收，避免使用后续日期训练。
- `plant_windows.json` 的抽取源为出钢计划、工序主表及 A/B/C 炉表。按有效计划、熔炼号、设备及工艺顺序对齐。转炉使用兑铁开始至出钢结束，LF 使用进处理位至出处理位，RH 使用处理开始至结束；实际吊起时间不进入工时估计。计划缺段、设备错配、事件逆序、非唯一匹配均不进入样本。历史实际使用的 LF/RH 设备号在回放中视为既定指派。
- 9 月 25 日至 10 月 4 日取得 543 个标定炉次块。10 月 5–7 日作为验证日期，10 月 8–11 日作为留出日期，各取一个含同浇次相邻炉的五炉窗口。程序追踪入选炉的全部吊运段。窗外其他炉的真实占位及整厂完整初始状态并未重建。内置窗口用于局部策略评估。
- `rail.json` 集中保存**假设**的工位坐标、五车初位、安全间距、档速、加减速度、限速区和转位准备时间。历史工时可以实测回放，行车运行结果仍是该配置下的模拟结果。示例覆盖转炉至连铸的重包任务；另外用专门用例检查空包回程的渡车限制。
- 需要从原始 Excel 重新抽取时，安装 `pandas openpyxl xlrd`，将上述五张表使用原文件名放入同一目录，运行 `python -m model.inputs.extract 原始表目录 data/plant_windows.json`。日常运行无需安装这三项依赖。

## 查看实验结果

`results/*_five_heats.json` 保存全部三组的 12 段样本结果和轨迹。每条 `lifts` 给出炉段、车号（1 至 5）、可吊/到位/起吊/落包时间。`results/*_holdout.json` 保存四个留出日期用实绩处理工时的配对回放，`results/timing_validation*.json` 保存不同分位数在验证集上的结果。计算耗时会随机器和负载变化。
